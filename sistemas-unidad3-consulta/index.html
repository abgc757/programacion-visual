3.1 Modelado orientado a objetos con UML

UML es un lenguaje de dibujos estándar para que todo el equipo entienda el sistema antes de programarlo.

DiagramaResponde a…Elementos clave
Casos de uso¿Qué puede hacer cada usuario?Actor (muñeco), caso de uso (óvalo), límite del sistema (caja), «include» (siempre ocurre), «extend» (a veces)
Clases¿Qué objetos hay y cómo se relacionan?Nombre, atributos (- nombre: str), métodos (+ publicar()), multiplicidad (1, *, 0..1)
Secuencia¿En qué orden se hablan los objetos?Líneas de vida, mensajes (flechas), respuestas (punteadas), alt para decisiones
Visibilidad: + público · - privado · # protegido. Relaciones: asociación (línea), composición (rombo lleno: «es parte de»), herencia (triángulo vacío: «es un»), dependencia (punteada: «usa»).

Receta para casos de uso: 1) lista quién usa el sistema; 2) lista qué quiere lograr cada uno (verbo + objeto: «Publicar artículo»); 3) dibuja; 4) escribe una ficha por cada caso (actor, precondición, flujo normal, flujo alterno, resultado).

Receta para clases: subraya los sustantivos de la descripción del sistema (candidatos a clases) y los verbos (candidatos a métodos).

3.2 Diseño de la base de datos

Modelo entidad-relación (ER): entidades (tablas), atributos (columnas), llave primaria PK (identifica cada fila), llave foránea FK (apunta a la PK de otra tabla) y cardinalidad (1:1, 1:N, N:M).

Normalización: ordenar las tablas para no repetir datos.

FormaReglaCómo lo notas
1FNUn solo valor por celda; sin grupos repetidosUna celda dice «lápiz, goma, regla»
2FNCada columna depende de TODA la llaveCon llave compuesta, una columna depende solo de una parte
3FNLas columnas no dependen de otras columnas que no son llaveEl nombre de la categoría se repite en cada artículo → crea tabla Categoría

N:M (muchos a muchos) siempre se resuelve con una tabla intermedia (ejemplo: Estudiante–Artículo mediante Solicitud).

Truco: si un dato se repite muchas veces y puede cambiar, ese dato pide su propia tabla.

3.4 Pruebas y validación del sistema

Verificación: «¿construimos bien el sistema?» (cumple el diseño). Validación: «¿construimos el sistema correcto?» (sirve al usuario).

NivelQué pruebaEjemplo
UnitariaUna funciónfiltrar() con lista vacía
IntegraciónVarias piezas juntasPublicar → guardar → ver en catálogo
SistemaTodo el programaRecorrer los 5 casos de uso
AceptaciónEl usuario real3 compañeros cumplen tareas sin ayuda

Caja negra: pruebas desde fuera (entrada → salida). Caja blanca: pruebas mirando el código (que cada rama se ejecute).

Partición de equivalencia y valores límite: en vez de probar todos los valores, prueba uno por grupo y los bordes. Si el nombre exige mínimo 3 letras: prueba 2 (inválido), 3 (válido, límite), 10 (válido) y vacío.

Caso de prueba = ID + condición + entrada + resultado esperado + resultado obtenido + (✔/✘). Un error encontrado se registra con pasos para repetirlo.

3.5 Documentación e implementación

Un sistema sin documentación se pierde cuando cambia el equipo.

DocumentoPara quiénContiene
Manual de usuarioQuien lo usaCómo instalar, pantallas, tareas paso a paso con capturas, preguntas frecuentes
Manual técnicoQuien lo mantieneArquitectura, diagramas UML/ER, estructura de archivos, cómo ejecutar pruebas
READMETodosQué es, requisitos, cómo ejecutarlo, autores, versión
Bitácora de cambiosEquipoVersión, fecha, qué cambió

Implementación = poner el sistema en uso. Estrategias: directa (se cambia de golpe), paralela (conviven viejo y nuevo), por fases (módulo a módulo), piloto (un grupo pequeño primero). Para Python: pip install pyinstaller y pyinstaller --onefile --windowed edu_share_Apellido.py genera un ejecutable en la carpeta dist.
